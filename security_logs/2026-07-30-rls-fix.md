# Security Incident / Compliance Review: RLS Misconfiguration on Internal Tables

**Date:** July 30, 2026
**Reviewer/Auditor:** N3MO Internal Security Audit
**Component:** Supabase / PostgreSQL Database

## Description of Finding
During a routine compliance and security review against the DPDP Act (India) and global privacy standards, it was identified that Row Level Security (RLS) was disabled on several internal tracking tables:
- `payment_orders`
- `rate_limits`
- `saas_repo_tracking`
- `webhook_deliveries`

Because our backend API leverages a privileged direct connection (bypassing RLS), the application functioned correctly, masking the fact that these tables were exposed to potential unauthorized reads via the Supabase anonymous (`anon`) REST API.

## Impact Analysis
- **Data Exposed:** Internal telemetry, webhook delivery metadata, rate limit counters, and payment order metadata.
- **Risk Level:** Medium. While no sensitive proprietary source code or PII was directly exposed in these tables, exposing internal billing and telemetry data violates the principle of least privilege and contradicts the strong security posture stated in the privacy policy.
- **Exploitation:** No known exploitation occurred. The issue was identified proactively during a policy-matching review.

## Remediation Applied
1. **RLS Enabled:** Row Level Security was explicitly enabled on all four tables via the following SQL migration:
   ```sql
   ALTER TABLE public.payment_orders ENABLE ROW LEVEL SECURITY;
   ALTER TABLE public.rate_limits ENABLE ROW LEVEL SECURITY;
   ALTER TABLE public.saas_repo_tracking ENABLE ROW LEVEL SECURITY;
   ALTER TABLE public.webhook_deliveries ENABLE ROW LEVEL SECURITY;
   ```
2. **Policy Configuration:** No public access policies (`USING (true)`) were created. By default, enabling RLS without policies establishes a "Deny All" rule for the `anon` and `authenticated` roles via the public API.
3. **Backend Verification:** Confirmed that the backend application does not rely on the `anon` key or public REST API for these tables, ensuring zero disruption to service availability.
4. **Policy Update:** The public-facing Privacy Policy was updated to accurately reflect the use of RLS and to explicitly address DPDP Act requirements (Grievance Officer, Retention Periods, Consent, and Cross-Border Data Flows).

## Future Safeguards
- All new database migrations must explicitly include `ENABLE ROW LEVEL SECURITY` for new tables.
- RLS audit scripts will be incorporated into the deployment checklist.
